# 从官方 Plane 1.4.2 迁到 1.5.0

`1.5.0` 是这条分支自己的版本，代码基线仍是官方 `release: v1.4.2`（`5f7d92784`）。它不是官方的下一个发行版。功能差异见 [自官方v1.4.2以来的改动.md](./自官方v1.4.2以来的改动.md)。

这次迁移只增加表和字段，不改已有工作项、状态名、周期关联和用户已选语言。部署时继续使用原来的 PostgreSQL，以及原来的 MinIO 或 S3。不要为了迁数据而改用 `plane.settings.workflow_local`。那套配置没有对象存储，旧附件会打不开，也不适合多进程生产环境。

## 迁移前核对

源环境必须已经是官方 1.4.2，并且数据库迁移已经执行到 `db.0122_alter_draftissue_assignees_alter_issue_assignees_and_more`。还停在更早迁移的库，先按官方 1.4.2 升级完，再做下面的步骤。

先备份数据库。备份完成前不要切流量。

在源库执行：

```sql
SELECT name
FROM django_migrations
WHERE app = 'db'
ORDER BY id DESC
LIMIT 5;
```

最新一条应是 `0122_alter_draftissue_assignees_alter_issue_assignees_and_more`。如果已经能看到 `0123` 到 `0126`，说明这四步以前做过，后面的 `migrate` 会跳过已记录的迁移，不要手工删记录再重跑。

## 部署

Web 和 API 一起换成这个仓库的 `1.5.0`。数据库连接、`SECRET_KEY`、对象存储和原来的 `WEB_URL` 保持不变。`SECRET_KEY` 一变，已登录会话会全部失效。

把实例版本设为：

```text
APP_VERSION=1.5.0
```

`register_instance` 用这个环境变量写入实例的 `current_version`。不设置时，界面上的实例版本不会自己变成 1.5.0。

然后只跑数据库迁移：

```bash
python manage.py migrate
```

相对官方 1.4.2，实际新增的是这四步：

| 迁移                                  | 作用                                 | 对已有数据                                              |
| ------------------------------------- | ------------------------------------ | ------------------------------------------------------- |
| `0123_project_workflow`               | 新建工作流配置表和业务角色表         | 不写入现有项目。工作流默认关闭                          |
| `0124_project_workflow_transition`    | 新建状态流转记录表                   | 空表                                                    |
| `0125_intake_template_config`         | 给 `intakes` 增加 `template_config`  | 已有 Intake 得到空对象 `{}`。缺这一列时，收集列表会 500 |
| `0126_profile_default_language_zh_cn` | 把新用户资料的语言默认值改成 `zh-CN` | 不改已经保存的 `language`                               |

迁移结束后再启动新的 API 和 Web。先打开一个已有项目、一条工作项和收集列表，确认能读到旧数据，再启用新功能。

## 已有项目会怎样

已有项目的状态、颜色和分组保持原样。官方项目里的 Backlog、Todo、In Progress、Done、Cancelled 不会被改成中文。

新建项目才会带上这套默认状态：需求完善、待做、开发中、开发完成、测试中、测试打回、完成、延期完成、取消、延期中、挂起，外加隐藏的 Triage。其中延期中和挂起属于 Cancelled 分组，但在工作流里仍是独立状态。

工作流要在项目设置里逐个打开。打开时只补缺失的状态和标签，不重命名、不删除。英文名 Backlog、Todo、In Progress、Done、Cancelled 会分别对上需求完善、待做、开发中、完成、取消，名字仍留在原处。库里若已有「等待测试」或「等待测试/开发完成」，会把它当作开发完成，不另建一个同义状态。对不上的状态才会新建，例如测试中、测试打回、延期中、挂起、延期完成，以及标签「类型/缺陷」和「阻断」。

因此，旧项目启用工作流后，主流程走的仍是原来的 Backlog、Todo 这些状态。想把旧状态改成中文名，需要在项目里手工改，这次迁移不会做。

不启用工作流时，状态选择和官方一样，没有角色限制。启用之后才出现产品、开发、测试、项目经理这四种业务角色；它们不改变 Admin、Member、Guest。项目经理可以在已配置状态之间跳转，但仍受未完成阻断子任务的拦截。连带完成子任务也只有项目经理能看到。

周期里的 Triage 任务本来就不显示。升级后，进度、总数和转移数量也不再计入这些任务。已经保存的周期快照不用改库，读取时会把总数收成待办、未开始、进行中、完成和取消的合计。

## 不要一起改的配置

对象存储继续用原来的 MinIO 或 S3。旧附件的地址依赖那套配置。

`plane.settings.workflow_local` 只用于没有 Redis、RabbitMQ 和对象存储的单机验证。生产环境不要把 `DJANGO_SETTINGS_MODULE` 改成它。

浏览器访问的主机名、API 的 `WEB_URL` 和前端的站点地址要一致。从 `127.0.0.1` 改成域名或局域网地址时，三处一起改，否则登录会因 CSRF 失败。

Webhook 订阅不会被迁移关掉。失败重试是新代码的投递行为，不需要改订阅数据。
